## 1. ステップ1：代表用途と選定理由

選ぶ用途は「メモリ上の受信バイト列を順次入力し、共通フレームの分割・構造検査結果を上位へ通知するオフライン解析部品」である。既存の[応答マスタ](current/RESPONSE_AND_NACK_MASTER.md)§2.2〜2.4を再利用でき、分割受信・連結受信・SUM・期限・ログ責務・決定的試験を小さな範囲で具体化できる。

| 項目 | 今回の範囲 |
|---|---|
| 入力 | 呼出元が用意したbytes。公開試験には合成データのみ使用 |
| 出力 | 構造検査済みフレームまたは解析上の診断を表す不変イベント列 |
| 接続 | OFFLINE。USB/COM・LAN/TCPを開かず、両者の受信単位を仮定しない |
| 対象機種・ROM | S201用Ver.1.17の共通フレーム形式に限定。実機機種・ROMは取得も推定もしない |
| コマンド | 送信コマンドなし。CMDは数値のまま保持し、ACK/NACKのpayload妥当性や成功を判定しない |
| 非対象 | 要求対応付け、応答待ち、タグ解析、アンテナ番号解釈、再送、設定変更、接続・ファイル入出力、GUI |

構造が正しいフレームは、機器がその内容を返すこと、NACKレイアウトが正しいこと、要求成功、実機接続成功の証明ではない。`FRAME`を`SUCCESS`へ読み替えない。本用途をユーザー提示の「範囲B・C」のいずれかへ勝手に割り当てない。

全18項目を一度に実装する代表用途ではない。応答timeoutと逐次要求の契約は次の層に残り、この設計だけで第2世代全体の完了とはしない。

| 型／メンバー | 契約 |
|---|---|
| Clock.now_ms() → int | 非負・単調非減少の整数ミリ秒。呼出元が注入する。実時間時計への暗黙fallbackなし |
| ParserOptions(frame_gap_timeout_ms=100) | 正の整数。bool不可。不変。100msはオフライン試行用の提案値で、機器の許容時間ではない |
| Frame | 不変。raw: bytes、address: int、command: int、data: bytes。addressの意味は推測しない |
| ParserEvent | 不変。kind: 下記の固定文字列、frame: FrameまたはNone、reason: 固定文字列またはNone、discarded_bytes: int |
| OfflineFrameParser(clock, options) | 空バッファで作成。時計は必須、optionsも明示して渡す |
| feed(data: bytes) → tuple[ParserEvent, ...] | 型確認後に時計を1回取得し、期限判定→入力解析の順で処理。全入力byteを同じ観測時刻とする |
| poll() → tuple[ParserEvent, ...] | 時計を1回取得し、未完候補の期限だけを判定する |

イベントは戻り値の順序付き列で上位へ通知する。コールバック・購読APIは作らず、再入や通知先例外を解析部品へ持ち込まない。上位がイベントを受けてログを保存する。rawには機密データを含み得るため、そのまま公開ログに出さない。イベントの既定repr等もraw/dataの内容を表示しない設計とする。

FRAMEのreasonはNone、discarded_bytesは0、frameは値を持つ。診断イベントのframeはNone、discarded_bytesは実際に破棄したbyte数とする。

kindの許容値はFRAME、NOISE、INVALID_FRAME、FRAME_GAP_TIMEOUT、INPUT_ENDEDの5つだけとする。TIMEOUTという別名は追加しない。例外と不正値の優先順位は§4.1に従う。コンストラクタは時計を読まない。最初の正当なfeed/pollが時刻比較の基準を作る。

## 4. ステップ4：一意な動作と期限

### 4.1 処理規則

1. feedはbytesのみ受け付け、bytearray・memoryview・文字列・NoneはTypeError。期限と時計の戻り値はboolを除くintのみを許し、型不正はTypeError、期限の0以下・時計の負値・時刻逆行はValueErrorとする。入力型→時計戻り値の型→値→単調性の順に確認し、失敗時に状態を変更しない。時刻が同じなのは許容。時計実装自身の例外はそのまま呼出元へ返し、状態は変更しない。optionsの型不正、clockに呼出し可能なnow_msがない場合はコンストラクタでTypeError。
2. 正当なfeed/pollでは、前回観測時刻を更新する。未完候補があり、現在時刻と最後にその候補へbyteを加えた時刻の差が期限以上なら、FRAME_GAP_TIMEOUTで候補全体を破棄する。空入力・pollはbyte到着時刻を更新しない。
3. STXより前のbyteは入力区間内の連続分をまとめ、NOISE（reason=BEFORE_STX）で破棄する。ノイズだけの入力は保存しない。
4. STXから4 byteが揃うまで待つ。LENから総長LEN+7を求め、揃うまで未完として保持する。DATA中のSTX/ETX/CRで分割しない。
5. 完成候補はETX→CR→SUMの順で検査し、最初の不一致だけをINVALID_FRAMEとして通知する。reasonはBAD_ETX／BAD_CR／BAD_SUM。先頭STXの1 byteだけを破棄し、残りを規則3から再走査する。INVALID_FRAMEのdiscarded_bytesは1であり、候補全長ではない。
6. 全検査が通ればFRAMEを1件返し、その候補全体を消費して続ける。CMDによる許可リストは設けず、未知値も数値で保持する。NACKの意味判定や長さ検査は上位の別契約とする。
7. 呼出し終了時には未完候補だけを保持する。同一呼出しで後ろのSTXへ再同期した場合、新しい候補の最終byte時刻はその呼出しの観測時刻とする。
8. finishは残りがあればINPUT_ENDED（reason=INCOMPLETE_FRAME）を1件返し、候補全体を破棄する。なければ空列。前回観測時刻の単調性チェック用状態は保持する。

FRAME_GAP_TIMEOUTのreasonはGAP_EXPIRED。受信の異常をAPI例外へ変換しない。未完は直ちにINVALID_FRAMEにしない。期限切れ・finishでは残りの内部STXから再走査せず全破棄する。

LENが255以下なので完成候補の最大長は262 byte。未完の保持上限は261 byteと導出できる。入力全体を内部バッファへ一括コピーせず逐次消費する設計とする。返却イベント数は入力サイズに比例するため、呼出元が大きいデータを分割する。この設計は破損LENにより後続フレームを一時的に巻き込む可能性を排除せず、失われたフレームを必ず復元できるとは保証しない。

### 4.2 timeoutを混同しない

| 種類 | 今回の扱い | 次の層への制約 |
|---|---|---|
| フレーム内timeout | 未完候補へのbyte追加間隔。既定案100ms、設定変更可。差が100msちょうどなら期限切れを先に処理 | USB/TCPの実時間への適用値として認定しない |
| 応答timeout | 対象外。要求を送信・登録しないので起点も既定値も設けない | 要求登録層で、要求の起点・完了条件・期限を別に定める。通知が来ただけで延長／成功にしない |

100msは再生処理における入力観測間隔の試行値であり、物理byte間隔を復元するものではない。同じfeed内のbyteごとの時刻は不明。実ログの到着時刻がない場合にtimeoutの実機評価をしない。

将来の要求層では「未完了要求を同時に1件」とする案を引き継ぐが、1要求1フレームとはしない。今回のparserにrequest_id、send、retry、success、応答タイマを追加しない。

## 5. ステップ5：10件の必須試験群の設計

### 5.1 記法と期待値の独立性

すべて合成の受信側構造データであり、実機からの応答例や送信可能なコマンドの提供ではない。F(C,D)は、ADR=00h、CMD=C、DATA=D、LEN=要素数、STX/ETX/CRを既存の共通形式に従わせ、SUMをSTX〜ETXの和の下位8 bitとした候補を表す。連結を「＋」、切出しを0起点の半開区間で表す。ここでは完成Hex列を掲載しない。

合成基準A=F(7Eh,空列)、B=F(7Eh,[11h])、M=F(7Eh,255個の11h)。未知CMDの選定は解析器の構造試験用で、7Ehの機器仕様上の意味を定義しない。期待raw/address/command/dataは入力定義と一致し、イベント順も比較する。

将来、試験データを具体化するときは原典に基づく独立計算でSUMと長さを確認し、解析器自身のSUM関数やフレーム生成処理を期待値生成に流用しない。現段階では試験は一件も実行していない。

TV-10は、設定作成では期限0／-1がValueError、True／1.0／文字列がTypeErrorであることを確認する。コンストラクタの不正options・now_msなしclockもTypeError。これらには既存parser状態が存在しない。

作成済みparserは10msでB[0:4]を保持した状態から始める。不正feed型の場合はclockの呼出回数が増えないこと、時計がTrue／1.0ならTypeError、-1／9ならValueError、時計が独自例外を送出すれば同じ例外が伝播することをそれぞれ確認する。各試行の失敗後は9msのpollが引き続きValueErrorとなり、次に10msでB[4:8]を渡すとFRAME(B)になることを確認する。これにより時刻逆行の拒否、同時刻の許容、未完bufferの保持を検査する。最終byte時刻の保持は、同じ失敗条件を新規parserで再現した別試行で、109msのpollは空列、110msのpollはFRAME_GAP_TIMEOUT(4)となることにより確認する。

追加の優先順位試験では、10msで先頭4 byteを保持後、110msに不正feed型を渡す。TypeErrorのみで時計は読まれず、その直後110msのpollで初めてFRAME_GAP_TIMEOUT(4)になる。呼出元がbytesへ変換する責務と、型不正を受信ノイズ扱いしない契約を確認する。

試験では制御時計を進め、Thread.Sleep、time.sleepや実時間を待つ処理を使わない。10件は試験群であり、表の全分割位置・全境界・全破損変種を実行して初めて「10群合格」とする。単に10個のassertで済ませない。

## 10. 採用理由・懸念点と推奨仕様（2026-11-20）

本節は既存の共通フレーム仕様と本用途の要件を基にした設計判断であり、外部ベンチマークや実機測定に基づく最適値の主張ではない。推奨仕様を採用する場合は各規則を必須契約として扱い、実装者がその場で別方式へ変更しない。今回の推奨提示だけで採用確定・実装許可とはしない。

### 10.1 100ms：合成入力プロファイルの既定値として維持する

| 候補 | 利点 | 懸念 | 判断 |
|---|---|---|---|
| 一律100msを実機にも適用 | 設定が一つで済む | 接続・記録粒度・スケジューリング等の影響を未検証。正常な受信片を破棄し得る | 不採用 |
| 既定値を置かず毎回指定 | 根拠のない暗黙値を防ぐ | 同じ試行でも値が変わりやすく、欠落時にAIが独自補完する余地がある | 今回の合成試行の標準にはしない |
| 期限無効を既定とする | 時刻のないデータでも処理しやすい | 期限契約・境界試験が通常経路から外れる。無効値の型・分岐も増える | 初版ではNone／0の無効モードを追加しない |
| 合成試行に限り100ms、明示optionsと注入時計を必須にする | 同じ入力・時系列で同じ結果を再現し、数値の所在を一つにできる | 100ms自体の性能上の優位性は根拠がない | 推奨 |

100msを50msや200msより優れているとは評価しない。既存試験案の99／100／101ms境界を維持して条件を固定するための初期値である。適切さの基準は、合成時系列の期待結果と一致すること。実機のbyte間隔の保証には使用しない。

推奨契約は、正の整数100msをParserOptionsの既定とし、parser作成時にoptionsを明示、作成後は変更不可とする。変更は候補をfinishして診断を回収した後、新しいparserを作成して行う。変更値・理由・時刻の意味を作業記録へ残し、TV-08と全試験群を再実行する。0・Noneによる暗黙の無効化、処理中の自動調整は導入しない。

| 入力の種類 | 時計と期限の扱い |
|---|---|
| 合成時系列 | 制御時計で指定時刻へ進め、100ms境界を検査する |
| 到着時刻が記録されたデータ | 記録にある観測時刻を同じ基準の整数msへ正規化して再生する。使用した粒度・同時刻の順序を記録。期限は解析条件であり物理故障判定ではない |
| 時刻のないバイト列 | 全feedで時計を0msに固定し、最後にfinishする。これは構造だけの解析で、時間経過の試験・実機timeout評価ではない。ファイル読み込みの所要時間を代用しない |

自動タイマは存在しない。期限はfeed/poll呼出し時に検査され、呼出しがなければ通知も起きない。finishは入力終了を優先し、時計を読まずINPUT_ENDEDにする。時刻なし解析で破損LENによる未完候補が残った場合も、finishで診断して破棄する。

### 10.2 API：同期3操作と戻り値イベントを維持する

| 選択 | 採用理由 | 懸念と扱い |
|---|---|---|
| feed／poll／finishの3操作 | 入力、時刻進行、終了を分け、隠れた動作を減らす | 呼出元がpoll/finishを忘れると通知されない。利用説明とTV-08/09で契約を明示 |
| Clock注入を必須 | OS時計や待ち時間に依存せず境界を再現できる | 時計実装にも契約が必要。型・負値・逆行・例外をTV-10で検査 |
| bytesのみ、不変Frame／ParserEvent | 入力の後書換えや結果の共有変更を避け、公開面を小さくする | bytearray等は呼出元で変換が必要。勝手な自動変換はしない |
| tupleによる順序付きイベント通知 | コールバックの再入・例外、バックグラウンド処理の順序を避ける | 戻り値を捨てれば記録も失う。呼出元は全イベントを順に回収する |
| 受信異常はイベント、API誤用は例外 | 正常に処理できた異常入力と、呼出し契約違反を区別できる | 種類の混在を防ぐため§4.1の例外優先順位と5種のkindを固定 |
| ログ保存は上位のみ | パーサをファイル形式・表示・公開方針から独立させる | bytesを含むFrameの保存は上位でマスク等が必要。既定表示へ生データを出さない |

今回はcallback購読、async generator、内部キュー、send/retry、reset、独自の万能エラー型を追加しない。大入力では戻り値tupleが大きくなるため、呼出元が分割する。固定の最大feed長は根拠なく新設しない。入力の分割でNOISEのイベント件数が変わり得るため、再現性にはbyte列だけでなくfeed境界・時刻・poll/finish順も含める。

finish後も同じparserを再利用できるが、時計の単調性基準は保持する。時刻を0へ戻して別の記録を扱う場合は新規parserを作る。並行・再入呼出しは契約外とし、同期化機構を解析部品へ追加しない。コールバックを排除しても、呼出元の誤用全般を自動防止できるとは説明しない。

### 10.3 再同期：完成不正候補は1 byte進め、未完の期限切れは全破棄する

| 候補 | 利点 | 懸念 | 判断 |
|---|---|---|---|
| 不正候補の全長を破棄 | 単純で高速 | 破損LENが後続の正常フレームを含んでいた場合、その開始位置まで捨てる | 完成候補の検査失敗には不採用 |
| 先頭STXの1 byteだけ破棄して再探索 | 誤った開始位置の内側にある次の候補を残せる。毎回必ず位置が進む | payload内のSTXを候補とするため、誤同期や複数診断が起き得る | 完成不正候補に推奨 |
| 任意のETX/CRまで飛ばす | 探索規則が短い | DATA内の値とフレーム末尾を混同する | 不採用 |
| エラー後は利用者が解除するまで停止 | 解析継続を誤認しにくい | オフラインの連結データを一度の破損で処理できなくする | 初版の既定にはしない |

推奨する判定順は、候補全長が揃う→ETX→CR→SUM。失敗した候補の先頭1 byteを捨て、残りをSTX探索へ戻す。新しい候補も全検査を通るまでFRAMEにしない。LENで定まる未完候補の内部にSTXがあっても、先回りして別フレームに切り替えない。

期限切れとfinishでは、未完候補全体を破棄して同じ古いbyte列を再解析しない。理由は、時間境界・入力区間の終了を一意に確定し、期限切れ診断の後で古い断片を新しい正常候補として扱わないためである。その代わり、破損LENの内部に正常フレームが隠れていても救出しない場合がある。これは明示的な損失条件として記録する。

懸念は、①加算SUMの一致だけで偶然の候補を完全排除できない、②壊れたLENによる待ちがあり得る、③復旧後FRAMEも実機由来・成功の証明ではない、④多くのSTXを含む入力では再検査が増える、の4点。初版で別の閾値や推測的なCMDフィルタを足さず、構造結果と意味解析を分ける。性能は未測定であり「高速」「全データ復元」を保証しない。

### 10.5 推奨仕様の要約と18項目への影響

### 11.1 イベントの検収表

略記の通知名だけで判定せず、次の全フィールドと順序を検収する。

| kind | reason | frame | discarded_bytes | 発生条件 |
|---|---|---|---:|---|
| FRAME | None | 検査したraw/address/command/data | 0 | 共通構造の全検査に合格 |
| NOISE | BEFORE_STX | None | 破棄した連続byte数 | STX探索で先行byteを破棄 |
| INVALID_FRAME | BAD_ETX / BAD_CR / BAD_SUMの最初の1つ | None | 1 | 完成候補が検査に失敗し、先頭STXだけ破棄 |

診断イベントの破棄数は正数。空bufferへのpoll/finishでは0 byteの診断を生成しない。受信異常をTypeError/ValueErrorへ変更せず、API誤用をNOISEへ変更しない。

| 状態・操作 | 次の状態・結果 | 検収先 |
|---|---|---|

Frameのrawとdataは呼出元への解析結果であり、秘匿・暗号化された値ではない。既定表示で隠すことはアクセス禁止ではなく、上位ログのマスク責務を置き換えない。

DOC-02の型定義は現資料版一覧を基準にする。rootはobject、local_documentsはobjectの配列、official_sourceはobject、path等は非空文字列、sha256は小文字16進64桁、size_bytesはbool以外の非負整数。reviewed_sectionsは非空文字列の配列、reviewed_printed_pagesはbool以外の正整数の非空配列、included_in_repositoryはfalseとする。repository_headは記録上の40桁16進コミットIDを検査するが、現在HEADとの一致を強制しない。ファイル未変更でも履歴は進み得るため、内容同一性はDOC-04で判断する。statusは現行の設計スナップショット状態を維持し、検査器が承認状態へ更新しない。

DOC-03の期待集合は§2.2の12資料を元に検査器側で定義し、検査対象JSON自身の行数やpathから生成しない。そうしなければ、JSONから資料を消すだけで欠落を隠せてしまう。AGENTSの入口手順で加わる資料はREVIEW-01で別途記録し、この12件への固定によって省略しない。

DOC-05は公開CIから公式PDFを自動ダウンロードしない。ローカルの原典照合はREVIEW-01で原本ハッシュと対象頁を確認し、PDF不在なら原典未確認として残す。CIで原典ID・ハッシュ欄が正しい形式であることと、実原本が一致することを分離する。

検査はファイルを修正せず、エラーには検査ID・対象path・理由を出す。終了コード案は0=選択した機械検査が合格、1=文書／資料不整合、2=引数・依存・実行環境の問題。どの検査を選択したかも出力する。これらは資料整合の判定であり、「実装開始可能」の終了コードではない。

実ファイルの改行やBOMもハッシュに含む。Windows作業コピーとLinux CIで改行が変われば不一致となるため、公開反映時にはcheckout時の改行方針を確認して、配布する実ファイルからスナップショットを取り直す。検査中の暗黙正規化や、CIを通すためだけの無審査の値更新はしない。現在の手元スナップショットが別環境でも一致すると保証しない。
