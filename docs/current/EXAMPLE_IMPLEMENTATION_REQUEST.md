# 実装依頼文の実例

## 1. 目的

この文書は、機種を限定しないRFIDタグ検知アプリのような、複数の落とし穴がある実装をAIコーディングエージェントへ依頼する際の、依頼文のテンプレートと書き方のポイントをまとめたものです。

実装依頼では、対象機種、接続方式、読み取り方式、アンテナ番号体系、NACK処理、停止時復元、未対応機種の扱いを明示してください。これらを省略すると、特定機種向けの前提を別機種へ流用したり、NACKをタグ未検知として扱ったり、未知機種でクラッシュしたりする実装になりやすくなります。

## 2. 依頼文テンプレート

```text
これは単発の作業です。過去のやり取りは考慮せず、この指示だけに従ってください。
以前作成した utr_tag_gui.py や utr_sun02_8ch_tag_gui など、既存のGUI実装は一切参照・流用しないでください。ゼロから作成してください。
参照するドキュメント:
https://github.com/TamaruNorio/UTR_RAG
このリポジトリをclone（または参照）し、README.md と AGENTS.md に書かれた案内に従って、実装に必要なコマンドカードや関連ドキュメントを確認してから実装してください。related_docs に列挙されているファイルは省略せず全部読んでください。
作りたいもの:
タカヤ製UHF帯RFIDリーダライタ向けの、機種を限定しないRFIDタグ検知GUIアプリ。
接続環境:
- USB/COM接続（COMポート番号とボーレートはGUI上で設定可能にする）
- 接続する機種は実行時までわからない前提とする（UTR-S201、UTR-SUN02-4CH、UTR-SHR201、UTR-SUN02V-8CH、UTR-SUN02-8CHのいずれかが繋がりうる）
要件:
1. 起動後、ROMバージョンを読み取り、シリーズ名から機種名を自動判定して画面に表示する
2. 機種によってアンテナの台数・番号体系（内部アンテナ番号の値域や対応関係）が異なることを踏まえ、機種ごとに正しい範囲・意味でアンテナを扱うこと。値域や意味を機種間で使い回さないこと
3. 各アンテナポートの接続状態を確認し、画面に一覧表示する
4. 接続されている全アンテナを使って、タグを連続的に検知できるようにする。単発コマンドの周期実行ではなく、公式アプリと同様の継続的な読み取り方式を採用すること。複数アンテナがある機種では、アンテナの自動切替の仕組みが動作モードによってどう働く/働かないかを踏まえて実装すること
5. 検知したタグを一覧表示する。表示項目：検知時刻、アンテナ、RSSI(dBm)、ANGLE、PC、EPC/UII
6. 検知結果をCSVファイルに保存できる
7. アンテナ断線などの異常が起きた場合、タグ未検知や他のエラーと混同せず、画面上ではっきり分かるように表示する
8. FLASH書き込み、出力設定変更、タグメモリ書き込みは実装しない（読み取り専用）
9. 停止時は、変更した設定（動作モード、使用アンテナ設定など）をRAM上で元の状態に戻す
10. 未対応の機種、または判定できない機種に接続された場合は、エラーで落とさず、その旨を画面に表示して安全側に倒すこと
出力先:
新しいフォルダに一式作成し、READMEに起動方法と、機種ごとのアンテナ台数・番号体系の扱いをどう実装したかを書いてください（requirements.txt、起動用スクリプト、簡単な自動テストも含める）。
完了したら、以下を報告してください:
1. 実装した機能の要約
2. UTR_RAGのどのドキュメント/コマンドカードを参照したか（ファイル名の一覧）
3. 機種ごとのアンテナ台数・番号体系の違いをどう実装で吸収したか
4. NACKエラーコード、特に0x68の扱いをどう実装したか
5. 連続的なタグ検知の方式（動作モード、アンテナ自動切替の扱い含む）をどう実装したか
6. 作成したファイル一覧とその場所
```

## 3. 各要件の意図

| 依頼文の該当箇所 | 防いでいる失敗パターン |
|---|---|
| 「これは単発の作業です。過去のやり取りは考慮せず」 | 過去の会話や別作業の前提を持ち込むこと |
| 「既存のGUI実装は一切参照・流用しない」 | 既存実装の機種依存や暫定処理をそのまま引き継ぐこと |
| 「related_docs に列挙されているファイルは省略せず全部読んでください」 | 関連ドキュメントの読み飛ばし |
| 「接続する機種は実行時までわからない前提」 | 実装時に特定機種へ固定してしまうこと |
| 要件1「ROMバージョンを読み取り、シリーズ名から機種名を自動判定」 | 接続機種を人手指定に頼り、ROM/シリーズ名と実機条件を確認しないこと |
| 要件2「値域や意味を機種間で使い回さないこと」 | 特定機種向けに作った実装を、内部アンテナ番号の値域が異なる別機種にそのまま流用してしまう間違い |
| 要件3「各アンテナポートの接続状態を確認」 | 物理的に未接続のアンテナを読み取り対象に含めること |
| 要件4「単発コマンドの周期実行ではなく...継続的な読み取り方式」 | 単発Inventoryの周期実行では実機でタグを継続的に検知できなかった実例 |
| 要件4「動作モードによってどう働く/働かないか」 | コマンドモードでは自動切替が働かない条件を見落とすこと |
| 要件7「タグ未検知や他のエラーと混同せず」 | NACK(0x68/CMD_ANT_ERROR)を「タグ未検知」と誤認した実装ミス |
| 要件8「FLASH書き込み、出力設定変更、タグメモリ書き込みは実装しない」 | 読み取り専用アプリに高影響操作を混入させること |
| 要件9「変更した設定をRAM上で元の状態に戻す」 | 停止後もリーダライタの設定が変更されたままになる問題 |
| 要件10「未対応の機種...エラーで落とさず」 | 未知の機種でアプリがクラッシュする問題 |
| 完了報告2「参照したドキュメント/コマンドカード」 | 実装者が必要なカードと関連文書を読んだか確認できないこと |
| 完了報告3「機種ごとのアンテナ台数・番号体系」 | アンテナ番号体系の実装方針が曖昧なままになること |
| 完了報告4「NACKエラーコード、特に0x68の扱い」 | 報告を求めることで、実装者(AI)がこの点を意識して実装するよう促す効果 |
| 完了報告5「連続的なタグ検知の方式」 | 単発Inventoryループか連続インベントリモードかが実装後に不明になること |

## 4. NACKエラーコード表の確認

このテンプレートを使っても、NACKエラーコード表（0x42/0x60など）を実際の値と取り違える間違いは再発したことがあります。実装時は、`RESPONSE_AND_NACK_MASTER.md` の「エラーコード1 一覧（完全版）」を確認し、`SUM_ERROR=42h`、`CMD_LBT_ERROR=60h`、`CMD_ANT_ERROR=68h` などの値を独自解釈で置き換えないでください。

## 5. 今後の更新

このドキュメントは実例の蓄積が目的です。新しい失敗パターンが見つかった場合は、依頼文テンプレート、各要件の意図、関連ドキュメントへの導線を追記していきます。
