# レスポンス・NACKマスタ

## 1. 目的

この文書は、UTR-S201シリーズの実装で必要になるレスポンス処理とNACK処理の考え方を整理します。

公式PDFが一次情報です。この文書は、AIに実装・レビューを依頼するときの補助資料です。

共通形式の出典は[公式PDF Ver.1.17](https://www.product.takaya.co.jp/dcms_media/other/TDR-MNL-PRC-UTR-S201-117.pdf) §5.1–5.4 p.98–101、NACKは§7.6 p.316–318です。2026-09-08に抽出テキストと照合しました。図表の目視照合・実機試験とは区別します。[照合範囲](SOURCE_REVIEW_STATUS.md)も確認してください。

## 2. 区別するレスポンス

実装では、少なくとも以下を区別してください。

- ACK
- NACK
- timeout
- 無応答
- 複数レスポンス
- 完了レスポンス
- 自動読み取りやRFタグ応答に伴う非同期レスポンス

### 2.1 呼称の統一

本文、コマンドカード、frontmatterでは、`ACK` / `NACK` / `TIMEOUT` / `NO_RESPONSE` / `COMPLETION` / `RF_TAG_DATA` / `ANT_SWITCH_COMPLETE` / `CARRIER_DETECTED` などの呼称を、可能な限り同じ意味で統一してください。同義表現を使う場合は、初出で正規呼称を併記し、frontmatterと本文で意味がズレないようにしてください。

RFタグ通信系では、1回の送信に対して複数フレームを受信する場合があります。単純な「1送信1応答」と決め打ちしないでください。

### 2.2 共通フレームと位置

PDF §5.1–5.2 p.98–99。送受信はバイナリで、LENはDATAのバイト数、総長はLEN+7 byteです。以下はフレーム先頭を0とするoffsetです。

| offset | フィールド | 定義 |
|---|---|---|
| 0 | STX | 02h |
| 1 | ADR | アドレス。送信と受信で役割を確認する |
| 2 | CMD | コマンド／応答の区分 |
| 3 | LEN | DATAのバイト数（0～255） |
| 4～3+LEN | DATA | LEN byte。LEN=0なら存在しない |
| 4+LEN | ETX | 03h |
| 5+LEN | SUM | 次節の加算値の下位1 byte |
| 6+LEN | CR | 0Dh |

受信ADRは通常リーダライタIDです。アンテナID出力が有効なRFタグ応答では読み取りアンテナ番号になります。ADRフィールド自体が省略・追加されるわけではありません。設定ACKやNACKへRFタグ応答のADR解釈を転用しません。

送信ADR=00hはリーダライタIDによらず処理する指定、00h以外は一致するIDの機器が処理する指定です（§5.2）。これは接続先とのプロトコル上のアドレスであり、LAN上の全IPへ送信する指定ではありません。

### 2.3 SUMの計算範囲

PDF §5.3 p.100。STXからETXまでの各バイトを加算し、下位8 bitだけをSUMにします。SUM自身とCRは加算しません。CRCや、Hex表記の文字列の文字コードを加算する方式ではありません。

PDF掲載例の算術確認は次のとおりです。送信フレームの新規作成例ではありません。

- `02h + 00h + 4Fh + 01h + 00h + 03h = 55h`
- `02h + 00h + 4Eh + 03h + 9Fh + 45h + 05h + 03h = 13Fh`、SUMは`3Fh`

予約バイトも受信した値のままSUM計算に含めます。「意味を無視する」と「計算から除外する」は別です。

### 2.4 フレーム受信と要求の完了

以下の受信設計は共通形式から導く実装上の注意です。USB/COM・LAN/TCPとも、1回の受信処理が1フレームと一致する前提を置きません。途中までの受信は蓄積し、LEN+7 byteの候補が揃ってから検査します。複数フレームが届いた場合は順に取り出します。DATAやSUM中の03h・0Dhを最初に見つけた位置で分割しません。未完の受信片を、直ちに不正な完成フレームと判定しません。

PDF §5.4 p.101では、コマンドモードは前のレスポンス受信後に次を送信し、一部コマンドはレスポンスを返さないとしています。自動読み取り中はRFタグデータがコマンド応答より先に届く場合があります。何をもって要求完了とするかは対象カードのPDF定義に従い、無関係な通知の受信で成功終了しません。

## 3. ACK解釈の前提

以下は関連し得る確認項目の一覧です。全項目がすべてのACKに適用されるわけではありません。[モード別適用範囲](RESPONSE_MODE_APPLICABILITY.md)と対象コマンドのPDF定義を併せて確認してください。

ACKは対象コマンドの長さ・詳細識別子・必要な種類やサブコマンドと照合します。設定で解釈が変わる応答について、起動時または実機送信前に必要な設定を確認します。固定長の設定ACKを解析するために、表の全項目を取得する必要はありません。未取得の設定をOFFと推測しないでください。

自動読み取り中は、モード読取りを含む通常の設定取得が保証されません。p.19–20の受付例外と[モード切替の条件](RESPONSE_MODE_APPLICABILITY.md)を先に確認します。コマンドモードへ戻す操作は動作変更なので、取得できない元設定を推測したり、観測のみの作業に停止を追加したりしません。

| 確認項目 | ACK解釈への影響 |
|---|---|
| ROMバージョン、シリーズ名、対象機種 | 対応コマンド、アンテナ系コマンド、レスポンス形式の前提を決める |
| 物理アンテナ容量、接続OKアンテナ | アンテナ番号を含む応答、アンテナ切替応答、アンテナエラーの解釈に使う |
| リーダライタ動作モード | コマンド応答と自動読み取り・非同期応答を切り分ける |
| アンテナID出力 | RFタグ応答のADRを読み取りアンテナ番号として解釈するかを決める |
| TID付加 | InventoryReadまたは連続インベントリリードの該当設定を確認する。通常Inventoryへ一般化しない |
| EPC/UII応答設定、EPCバッファリング | RFタグ応答の出力単位、蓄積応答、後続応答の有無を決める |
| 自動読み取りのサイクル終了通知 | 自動読み取り中の枚数応答の有無を決める。単発Inventoryの完了応答とは分ける |
| アンテナ切替完了応答 | 自動切替時の切替完了ACKを待つべきかを決める |
| キャリア検知応答 | 他キャリア検知イベントを受信対象に含めるかを決める |
| RAM設定かFLASH設定か | 一時変更、復元、再起動後保持の扱いを決める |

byte位置はフレーム先頭からかDATA先頭からかを明記し、対象応答の定義に従ってください。設定により意味が変わる箇所だけを条件分岐させます。固定長フィールドまで任意に変化すると推測しないでください。

## 4. 設定依存レスポンスの代表例

| 条件 | 実装上の扱い |
|---|---|
| アンテナID出力ON | 該当するRFタグ応答のADRを読み取りアンテナ番号として解析する |
| アンテナID出力OFF | ADRはリーダライタID。フィールドを削除せず、前回の設定値だけで実受信ANTを断定しない |
| TID付加OFF | 対応するInventoryRead系応答のTID長・領域を該当節で確認する |
| TID付加ON | 対応するInventoryRead系応答のTID領域を解析する。すべてのInventory応答へ一般化しない |
| 自動読み取りのサイクル終了通知ON | 各サイクルの枚数応答を受信する。受信セッション全体の終了にはしない |
| 自動読み取りのサイクル終了通知OFF | 自動読み取りの枚数応答を必須条件にしない。単発Inventoryの完了応答には適用しない |
| アンテナ切替完了応答ON | 自動読み取りで使用アンテナ全体の切替終了通知を受信対象に含める。切替方式の条件も確認する |
| アンテナ切替完了応答OFF | 切替完了ACKが返らないことを異常扱いしない |
| キャリア検知応答ON | 自動読み取りで他キャリア検知イベントを受信対象に含める。コマンドモードは別のNACK条件に従う |
| キャリア検知応答ONかつイベント0件 | 周囲に他キャリアがない場合は正常な未観測として扱う |
| キャリア検知応答OFF | キャリア検知イベントが返らないことを異常扱いしない |

UTR-SUN02-4CH / USM02 Ver.2.052に関する従来の「確認済み」記述は、[過去のGUI制作記録](UTR_TAG_GUI_IMPLEMENTATION_FEEDBACK.md)に由来する履歴です。今回の文書照合では再試験しておらず、個別の試験条件・証跡がない範囲を実機確認済みと補いません。[確認状態の記録方針](VERIFICATION_POLICY.md)に従います。

自動読み取りモード（passive receive/listen）でも、設定により読み取りサイクル終了時の枚数応答が返ります（PDF §7.1 p.114、§7.2 p.120、§7.4.25 p.233–234）。通知OFFなら不在は正常ですが、設定不明なら判定保留、ONなら観測条件を調べます。単発コマンドの完了と、連続処理中のサイクル通知を分けてください。詳細は[モード別適用範囲](RESPONSE_MODE_APPLICABILITY.md)を参照してください。

## 5. コマンドカード内のHex例の読み方

各コマンドカードには、実装時に迷いやすいACK、NACK、RFタグ応答、完了応答の例を記載します。

| 表記 | 意味 |
|---|---|
| `TX` | 上位機器からリーダライタへ送信するコマンド例 |
| `RX` | リーダライタから上位機器へ返るレスポンス例 |
| `02` | STX |
| `ADR` | レスポンスのアドレス位置。通常はリーダライタID。アンテナID出力ONのRFタグ応答では読み取りANT番号になる |
| `30` | ACK |
| `31` | NACK |
| `6C` | RFタグ読み取りデータなどの非同期・タグデータ系レスポンス |
| `LEN` | データ部バイト数 |
| `SUM` | STXからETXまでの加算値の下位1 byte（§2.3） |
| `0D` | CR |
| `<...>` | 可変長データまたはPDF該当節で定義されるフィールド |

PDFに完成Hex例があるものは、カード内に完成Hex例として記載します。PDF例がない、または設定値によりACKデータ部が変わるものは、完成Hexとして誤読されないように構造例で示します。

実機ログ由来のraw EPC / UII / TID、顧客タグ固有値、製造番号、パスワードはGitHubに載せません。PDF掲載例または説明用の固定例として扱える値だけを記載してください。

## 6. NACK処理

NACKは機器が返すエラー応答です。上位アプリの待機期限切れ（TIMEOUT）とは別です。コード1の02hはタグ受信の中断、60hはLBTのキャリアセンス時のタイムアウトであり、ホストの通信待機期限切れに置き換えません。

単発UHF_Inventoryの正常0枚は読取完了ACKの枚数0000です。NACKの04h（RFタグ無応答）や68h（アンテナ断線）を正常0枚の代用にしません。個別コマンドで返り得るNACKと対応ROMは、対象カードと原典で確認します。

### 6.1 NACKの固定レイアウト

PDF §7.6 p.316。CMD=31h、LEN=0Ah、総長17 byteです。DATA先頭を0とする位置は次のとおりです。

| DATA offset | フィールド | 解釈条件 |
|---|---|---|
| 0 | 詳細コマンド | エラー発生に対応する詳細識別子 |
| 1 | エラーコード1 | 主エラー |
| 2 | エラーコード2 | コード1が0Ahの場合に解釈する |
| 3 | エラーコード3 | UHF_EncodeまたはUHF_BlockWrite2。意味はコマンドで異なる |
| 4 | エラーコード4 | UHF_BlockWrite2かつコード3が0Ahの場合に解釈する |
| 5～9 | 予約 | 通常00h。非ゼロでも意味は無視する |

追加エラーの解釈条件を満たさなくても、固定フィールドを削除してLENを短縮しません。予約5 byteは非ゼロの場合もあると注記されています（p.316 ※5）。ゼロ以外を理由にNACKを破棄したり、独自のエラー状態に割り当てたりしません。SUM検査にはその値も含めます。

NACKのDATA[1]はサブコマンドやパラメータ種類ではありません。設定ACKのレイアウトを流用せず、送信要求の文脈と詳細識別子で対応を確認します。LENが0Ahと異なる候補は、共通NACKとして解析を完了しません。未知のコードも値を保持したエラーとして扱い、成功へ読み替えません。

### 6.2 エラーコード1／BlockWrite2のコード3

PDF §7.6 p.317の11値です。UHF_BlockWrite2のコード3にも同じ表を使用します。その場合、0Ahの追加情報はコード2ではなくコード4を確認します。

| コード | シンボル | 意味 |
|---|---|---|
| 01h | CMD_CRC_ERROR | RFタグから受信したデータのCRCが一致しない |
| 02h | CMD_TIME_OVER | RFタグからの受信データが途中で途切れた |
| 03h | CMD_RX_ERROR | アンチコリジョン処理中にエラーが発生した |
| 04h | CMD_RXBUSY_ERROR | RFタグからの応答がない |
| 07h | CMD_ERROR | コマンド実行中にリーダライタ内部でエラーが発生した |
| 0Ah | CMD_UHF_IC_ERROR | RFタグアクセス時、リーダライタ内蔵チップがエラーを返した（エラーコード2をあわせて確認） |
| 42h | SUM_ERROR | 上位機器から送信されたコマンドのSUM値が不正 |
| 44h | FORMAT_ERROR | 上位機器から送信されたコマンドのフォーマットまたはパラメータが不正 |
| 60h | CMD_LBT_ERROR | キャリアセンス時、タイムアウトでキャリアを送信できなかった |
| 64h | HARDWARE_ERROR | ハードウェア内部で異常が発生した |
| 68h | CMD_ANT_ERROR | アンテナ断線検知時にRFタグ通信コマンドを送信した（アンテナ接続、使用CHと実際の接続CHの一致、ケーブル状態を確認） |

### 6.2.1 p.64・65の欄名訂正（保守者確認済み）

2026-09-09の保守者訂正により、p.64の[81h: ハンドル取得失敗]、p.65の[04h: メモリロック]は、いずれも「エラーコード2」です。これらのRFタグ通信エラーではエラーコード1に[0A]hが返ります。コード1=04h（RFタグ無応答）とは区別します。

p.64の名称は「RFハンドル取得失敗」から「ハンドル取得失敗」へ訂正し、コードのコロン直後に半角スペースを入れます。81hはQuery実行時にRFタグのハンドル情報を取得できなかったことを表します。[訂正本文と記録](SOURCE_REVIEW_STATUS.md)のOPEN-013を参照してください。

### 6.3 エラーコード2／BlockWrite2のコード4

PDF §7.6 p.317。コード2はコード1=0Ah、UHF_BlockWrite2のコード4はコード3=0Ahの場合にこの表で解釈します。下記は原典の意味を簡潔に示したもので、同じ値でもコード1の表とは意味が異なります。

| 値 | 意味 |
|---|---|
| 01h | 非対応 |
| 02h | 権限不足 |
| 03h | メモリオーバーラン |
| 04h | メモリロック |
| 05h | 暗号違反 |
| 06h | コマンドのカプセル化なし |
| 07h | レスポンスバッファオーバーフロー |
| 08h | セキュリティアウト（原典の名称） |
| 0Bh | 電力不足 |
| 0Fh | 非特定のエラー |
| 20h | Write失敗 |
| 22h | Kill失敗 |
| 23h | Lock失敗 |
| 80h | 検出されない |
| 81h | ハンドル取得失敗 |
| 82h | Accessパスワードエラー |
| 90h | CRCエラー |
| 上記以外 | 処理失敗。受信値を保持する |

#### BlockWrite2のコード対と成功Word数

[BlockWrite2カード](commands/cards/55_1d_uhf_block_write2.md)では、NACKのDATA[1]/[2]がコード1/2、DATA[3]/[4]がコード3/4です。コード3はコード1と同じ表を使用し、コード3=0Ahの場合の詳細はコード4を参照します。Encodeのコード3の「失敗領域」表を流用しません。成功Word数・失敗Word位置は定義されていません（p.316–318）。

[BlockWrite](commands/cards/55_1a_uhf_block_write.md)には、途中失敗のNACKでも一部書込み済みの場合があるとp.284に明記されています。BlockWrite2にも原子的更新・巻戻しの保証を追加せず、応答と確認できた状態を分けます。

### 6.4 Encodeのコード3

PDF §7.6 p.318。UHF_Encodeのコード3は内部処理の失敗箇所です。BlockWrite2用のコード3表を使いません。

| 値 | 失敗箇所 |
|---|---|
| 01h | Reserved領域への書込み |
| 02h | EPC/UII領域への書込み |
| 03h | User領域への書込み |
| 05h | Lockコマンド発行 |

この表には04hの定義がありません。値を連番と想定して意味を補いません。コード3はフレームoffset 7（8 byte目）で、成功Word数や失敗Word位置ではありません。Encodeではコード4をBlockWrite2用の追加情報として解釈しません。

[Encodeカード](commands/cards/55_1e_uhf_encode.md)の処理順・パスワード保持表を併せて確認します（p.294–300）。同じコード3=02hでも、非ゼロパスワード書込みならReserved後、ゼロ書込みならReserved前の失敗です。NACKでも部分書込み済みの可能性があり、リーダ側パスワードの復帰をタグの巻戻しと同一視しません。

## 7. 実装時の注意

- timeout値を固定値だけで扱わず、接続方式とコマンド種別に応じて設定する。
- ACK、NACK、timeout、無応答を同じエラーとして扱わない。
- NACK時はエラーコードをログに残す。
- 複数レスポンスがあるコマンドでは受信ループを設計する。
- 完了レスポンスがあるコマンドでは、完了を受けるまで処理を閉じない。
- ACKパーサは必要な要求文脈・設定を入力に取り、固定長応答と設定依存応答を区別する。NACKは§6の固定形式と解釈条件に従う。
- 自動読み取り中は、コマンド応答、タグ応答、読取完了応答、アンテナ切替完了応答、キャリア検知応答を同じ受信ループ内で分類する。
- キャリア検知イベント0件や、切替完了応答OFF時の切替完了ACKなしは、設定どおりなら異常扱いしない。TID付加OFFでもInventoryReadのTID長フィールドは残るため、[TIDと単位](TID_MEMORY_AND_UNITS.md)と対象カードで確認する。

## 8. AI実装用パーサ契約

共通部分は本書、コマンド固有部分は各カードの `AI実装用レスポンス定義` とPDF該当節で確認します。カードには未照合の汎用説明が残るため、本書と矛盾する場合にカードを無条件で優先しません。

| 段階 | 判定 |
|---|---|
| フレーム候補の検査 | LEN+7の総長、STX/ETX/CR、SUMを確認。不正な完成候補はINVALID_FRAME |
| 応答区分 | CMD=31hはNACK形式を確認。CMD=6Chは対象のRFタグ応答定義へ。CMD=30hは次の詳細分類へ |
| ACKの詳細分類 | 対象・モード・LEN・DATAを照合し、通常ACK、COMPLETION、ANT_SWITCH_COMPLETE、CARRIER_DETECTED等へ分類する |
| 要求との対応 | 必要な識別子・種類・値が対象要求と一致するか、要求を終える応答かを確認する |

CMD=30hというだけでは、送った要求の成功と判定しません。単発のCOMPLETIONと、自動読み取り中のサイクル通知を分けます。未対応のCMDや詳細識別子は未分類のまま保持し、成功にしません。

TIMEOUTはフレームの種別ではなく、必要な応答が期限内に揃わない場合の待機結果です。非同期通知が届き続けても、対象応答が欠ければ要求は未完了です。NO_RESPONSEも受信フレームではなく、仕様上正常時に応答を返さない要求の方針を表します。異常時のNACK有無や復旧条件まで「一切応答なし」と一般化せず、個別カードで確認します。

### リスタートとFLASH初期化の応答差

[リスタート9Dh](commands/cards/4e_9d_restart_reader.md)はACK/NACKとも返しません（p.148）。無応答は想定内ですが実行成功の証拠ではありません。次コマンドまで2秒以上空け、ROM読取り等による通信確認と設定反映確認を分けます。ROM読取り成功だけで再起動そのものを証明しません。

[FLASH初期化6Fh](commands/cards/4e_6f_flash_initialize.md)はCMD=30h・LEN=01h・DATA[0]=6Fhの固定ACKです（p.149）。値や再起動完了フラグは含まず、実行後はリスタートまたは電源再起動が必要です。6Fhのtimeoutを9Dhと同じ正常無応答として処理しません。失敗時の未変更も保証せず、自動再送を避けます。

### 診断結果の異常とNACK

[エラー情報読取り](commands/cards/4f_80_read_error_info.md)はLEN=04h・80hのACKで、DATA[1]の00hが正常、非ゼロが装置異常です。DATA[2～3]は予約で、p.123の例の09h・03hをNACKの追加コードとして解釈しません。非ゼロでもフレームはACKです。

[CheckAntenna](commands/cards/55_44_uhf_check_antenna.md)はLEN=03h・44hのACKで、DATA[1]が要求番号、DATA[2]が00h=接続OK／01h=接続エラー／02h=存在しない番号です（p.138–139）。01h・02hをNACKに変換しません。これらのACK内結果、CMD=31hのNACK、timeout、正常なタグ0枚は別の区分です。

### Handleの読取りと透過応答

[GetHandle](commands/cards/55_46_uhf_get_handle.md)はCMD=30h・LEN=03h・詳細46hと2 byte Handleの固定ACKです。MSB firstで読み、返却値だけで現在のタグと一致するとは判断しません（p.150–151）。

[ThroughCmd](commands/cards/55_ff_uhf_through_cmd.md)の受信データありACKはFFh・動作パラメータ・受信bit長2 byte・可変bit列です（p.309）。bit列は上位詰めで、端数下位bitを除外します。リーダACKと透過先のタグ処理結果を分け、タグのエラー形式を共通NACKに読み替えません。送信のみとCRC省略時の長さはOPEN-027／028で保留し、空ACKや正常無応答を補いません。
