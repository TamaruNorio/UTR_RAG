# R9-2 Multi-language Implementation Guide

## 1. 目的

UTR-S201向けRAGをPython専用ではなく、複数言語で安全に実装方針へ展開できる社外レビュー候補向け資料にする。

## 2. 対象範囲

- Python
- C#
- C++
- JavaScript / Node.js
- PowerShell
- 日本国内向け、日本語利用者向け、日本の電波法準拠機器向けの実装検討

## 3. 日本国内向け前提

海外利用、海外設置、海外販売、海外周波数、海外認証は対象外である。地域条件が不明な場合は日本国内仕様を前提にし、海外用途が示された場合は `HOLD` とする。

## 4. Pythonの実装方針

- 主な用途: 検証、サンプル、ログ取得、CSV保存。
- 想定利用者: 技術検証担当、評価担当。
- 向いている場面: 机上検討から小規模実機確認まで。
- 向いていない場面: 長期運用の業務アプリ本体。
- 通信方式の考え方: USB/LAN/Serialを設定値として外部化する。
- タイムアウト処理: 接続、送信、受信を分けて設定する。
- ログ出力: 接続、送受信概要、タイムアウト、例外、切断を記録する。
- 例外処理: ポート未接続、応答なし、NACK、パース失敗を分ける。
- 設定値の外部化: COM、baudrate、IP、ポート、回数、CSV保存先を外部化する。
- 実機確認時の注意点: タグ固有IDをマスクし、既存設定から確認する。
- Level 4以上の注意: 明示確認なしに周波数、送信出力、Inventory Paramを変更しない。

## 5. C#の実装方針

- 主な用途: Windows業務アプリ、GUI、サービス連携。
- 想定利用者: 業務アプリ開発者、SI担当。
- 向いている場面: 国内業務アプリでの需要が高い可能性がある。
- 向いていない場面: 短時間の試行錯誤だけを目的にした検証。
- 通信方式の考え方: SDK利用可能環境ではSDKを第一候補とする。
- タイムアウト処理: UIスレッドをブロックしない設計にする。
- ログ出力: 操作ログ、通信概要、エラー、再接続を残す。
- 例外処理: ユーザー表示と内部ログを分ける。
- 設定値の外部化: 接続先、読み取り条件、ログパスを設定ファイルまたはUIで管理する。
- 実機確認時の注意点: PoC、評価、本番導入判断を分ける。
- Level 4以上の注意: 管理者確認と復旧手順なしに実装しない。

## 6. C++の実装方針

- 主な用途: ネイティブ制御、低レベル通信、既存制御アプリ統合。
- 想定利用者: 制御系開発者。
- 向いている場面: 性能、既存資産、OS依存制御が重要な場合。
- 向いていない場面: 仕様確認が未完了の初期検証。
- 通信方式の考え方: 通信層、プロトコル層、アプリ層を分ける。
- タイムアウト処理: ブロッキングを避け、終了条件を明確にする。
- ログ出力: バイナリ詳細ではなく、マスク済み概要を基本とする。
- 例外処理: 戻り値、例外、エラーコードの方針を統一する。
- 設定値の外部化: ビルド時固定を避け、運用設定として管理する。
- 実機確認時の注意点: 小範囲の既存設定確認から始める。
- Level 4以上の注意: 承認、復旧、ロールバック手順を設計に含める。

## 7. JavaScript / Node.jsの実装方針

- 主な用途: Webhook、API連携、ダッシュボード連携。
- 想定利用者: Web/API開発者。
- 向いている場面: 読み取り結果の通知、Web連携、後処理。
- 向いていない場面: 実機制御をブラウザだけで完結させる構成。
- 通信方式の考え方: 実機制御プロセスとWeb連携を分離する。
- タイムアウト処理: Promise/イベント処理で接続、送受信、外部APIを分ける。
- ログ出力: 個人情報、タグID、認証情報をマスクする。
- 例外処理: 通信失敗とWebhook失敗を分ける。
- 設定値の外部化: 環境変数や設定ファイルに分離する。
- 実機確認時の注意点: 先に模擬データで連携確認する。
- Level 4以上の注意: Webhook処理からRF条件変更を直接実行しない。

## 8. PowerShellの実装方針

- 主な用途: Windows現場検証、運用補助、ログ収集。
- 想定利用者: 現場担当、保守担当。
- 向いている場面: 接続確認、ファイル操作、簡易検証。
- 向いていない場面: 複雑な業務アプリ本体。
- 通信方式の考え方: 実機制御は既存ツールまたはSDKを優先する。
- タイムアウト処理: コマンド実行時間、通信待ち、ファイル出力を分ける。
- ログ出力: 実行日時、対象、結果、エラーを記録する。
- 例外処理: 終了コードと例外メッセージを残す。
- 設定値の外部化: パラメータ化し、スクリプト内固定を避ける。
- 実機確認時の注意点: 管理者権限や実行ポリシーの影響を記録する。
- Level 4以上の注意: スクリプト自動実行で設定変更を走らせない。

## 9. 各言語で共通して守るべき通信処理

- 接続、送信、受信、切断を分ける。
- タイムアウトを必ず定義する。
- NACK、応答なし、パース失敗を分ける。
- ログはマスク済み概要を基本にする。
- 設定値は外部化する。

## 10. 各言語で共通して守るべき安全処理

- Level 4以上は明示確認なしに実装しない。
- Level 5は明示承認と復旧手順なしに進めない。
- 完成Hex、SUM計算済みコマンドをRAG内に残さない。
- 実機送信用コードは対象言語の実装リポジトリまたは利用者環境で作成する。

## 11. 実機確認前に確認すること

- 対象機器
- 接続方式
- 接続情報
- 日本国内仕様の範囲
- 読み取り対象
- 設定変更可否
- ログ保存方針
- 復旧方法

## 12. HOLDにする条件

- 対象機器、接続方式、地域条件が不明
- 海外利用が示されている
- Level 4以上の明示確認がない
- FLASH保存の承認と復旧手順がない
- PDF正本との照合が必要
- コマンド仕様が不明
